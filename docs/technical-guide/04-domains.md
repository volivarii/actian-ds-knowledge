# The domains

Each domain end to end: what a person writes, which generator reads it, what comes
out, and which schema governs it.

*Counts read at knowledge v0.34.166 on 2026-09-01.*

## How to read a domain

`domains.json` is the per-domain authoring contract and the fastest way to
understand a domain you have not seen. For each of its 12 units it declares five
things:

| Field | Means |
| --- | --- |
| `src` | The glob a person edits |
| `generator` | The script that reads it |
| `frontmatterSchema` | What validates the typed block at the top, or `null` where there is no markdown |
| `body` | What happens to the prose: `parse` (`sections` or `none`), `mirror` (is it copied verbatim to dist), `field` (which single field absorbs it) |
| `distShape` | `per-record+bundle`, `pattern-H-tree`, `single-object`, or `embedded` |

It is hand-authored, governed by `schemas/domains.json`, and checked by
`scripts/validate/validate-domains.js`.

**One entry is currently wrong.** The `tokens` unit declares
`src: tokens/tokens.json` and `generator: null`, but `tokens.json` is itself
generated by `scripts/tokens/derive-tokens.js` from `foundations/src/`. The unit
describes an output as though it were the source. See the Tokens section below for
what actually happens. A domain that registers no unit has to earn
that exemption: the identity ledger is exempt because it has no authoring surface,
and the honesty of that exemption is paid for by a freshness guard in the required
check instead.

## The register

| Unit | Source | Generator | Body treatment | Dist shape |
| --- | --- | --- | --- | --- |
| `categories` | `components/src/categories/*.md` | `derive-categories.js` | mirrored verbatim | per-record plus bundle |
| `foundations` | `foundations/src/*.md` | `derive-foundations.js` | parsed into sections, also mirrored | Pattern H tree |
| `accessibility` | `accessibility/src/*.md` | `derive-a11y-sections.js` | parsed into sections | Pattern H tree |
| `guidelines` | `components/src/*/{content,usage,design,behavior}.md` | `derive-guidelines.js` | parsed into sections, kept verbatim per domain | per-record plus bundle |
| `app-context/apps` | `app-context/src/apps/*.md` | `derive-app-context.js` | parsed into H2 and H3 sections | single object |
| `app-context/entities` | `app-context/src/entities/*.md` | `derive-app-context.js` | absorbed into `description` | single object |
| `app-context/patterns` | `app-context/src/patterns/*.md` | `derive-app-context.js` | absorbed into `description` | single object |
| `content/global` | `content/src/{writing,product}/*.md` | `derive-content.js` | concatenated verbatim | single object |
| `content/patterns` | `content/src/patterns/*.md` | `fanout-patterns.js` | parsed into sections, appended into component records | embedded |
| `graph` | none | `derive-graph.js` | reads no prose | single object |
| `tokens` | `tokens/tokens.json` | none | no markdown | single object |
| `canonical-sections` | `components/src/canonical-sections.json` | `derive-canonical-sections.js` | no markdown | single object |

Two entries in that table are worth pausing on. **`content/patterns` is the only
`embedded` shape**: its sections are fanned out and appended into component
guideline records rather than emitted as their own artifact, so a change there
shows up in files that name a different domain. And **`graph` has no source at
all**, because it is a projection of other domains' dist. Chapter 06.

## Foundations

7 sections, ordered by `foundations/src/_order.json`: intro, table of contents,
color primitives, tokens, design guidelines, handoff protocol, related guidelines.

Derives a Pattern H hierarchical tree: a per-leaf JSON for every heading path, an
`_index.json` at every branch for navigation, a `foundations.bundle.json` roll-up
for one-shot reading, and a `foundations.md` concatenation. The concatenation is
synthesized rather than byte-verbatim, which matters if you are diffing it.

Foundations is also a **referenced** taxonomy: components point into
`foundations-index.json` by slug through `foundations_refs`.

Schema: `schemas/foundations.json` for frontmatter, `schemas/section.json` for the
derived sections.

## Components

The largest domain and the only one with all three origins.

### Authored: per-component guidelines

Each of the 54 components in `components/src/<slug>/` has a `_meta.yml` plus
whichever domain files it needs:

```yaml
component: "Buttons"
category: action
a11y_refs:
  - { ref: buttons }
domains:
  content:  { status: approved, owner: content-team }
  usage:    { status: approved }
  design:   { status: draft, owner: design }
  behavior: { status: draft }
  tokens:   { status: approved }
```

Five authorable domains: `content.md`, `usage.md`, `design.md`, `behavior.md`, and
`tokens.yml`. Four statuses:

| Status | Means | The domain file |
| --- | --- | --- |
| `approved` | Written and signed off | must exist |
| `draft` | Written, not reviewed | must exist |
| `inherited` | The component takes its category's shared guidance | must **not** exist |
| `not-started` | Declared but empty: a visible debt marker | must **not** exist |

Two things people get wrong here. **`inherited` is not a gap.** A coverage number
that counts it as missing overstates the debt, and it is the right answer for most
Design and Behavior domains. **It is only valid where the category defaults
actually carry that domain**: Behavior resolves to motion and a11y refs, Design to
anatomy and variant axes. Usage and Tokens have no category-level default, so an
unwritten one is `not-started`, never `inherited`.

Status is normally derived rather than hand-set: it is inferred from whether the
domain file exists, and `owner` and `updatedAt` come from git. The Editor manages
this. Explicit values are still accepted as substrate input.

### Authored: category defaults

7 files in `components/src/categories/`. Each carries, in typed frontmatter: the
category anatomy, the variant axes and their values, the transversal refs
(`a11y_refs`, `motion_refs`, `foundations_refs`), an `authoring_status`, a
`confidence` block scored per facet, and a `last_reviewed` date. The body below is
the design rationale, mirrored verbatim to dist.

A ref picked once on a category applies to every component in it. That is the
leverage: `schemas/category-defaults.json` requires `motion_refs` and `a11y_refs`
and supports `foundations_refs`.

### Synced from Figma

| Artifact | What it is |
| --- | --- |
| `dist/registries/` | 3 registries: `dskit.json`, `fmkit.json`, `metakit.json`. Keys, variants, properties |
| `dist/categories.json` | The category assignment as Figma states it |
| `dist/anatomy/` | 179 per-component geometry trees |
| `dist/media/<slug>/preview.webp` | The component's Preview frame, captured |
| `dist/media/<slug>/default.webp` | The default variant captured in isolation, resolved from the anatomy dist |
| `dist/icons/`, `dist/graphics/` | 146 icons and the color-preserving artwork, each with a `.degraded.json` sibling recording what could not be captured |
| `dist/text-styles.md`, `dist/effect-styles.md` | Style catalogues |

The `.degraded.json` siblings are the pattern to copy for any future capture: the
failure to capture something is recorded as data rather than dropped, so a
regression in capture quality is visible instead of looking like absence.

### Derived

`dist/guidelines/` holds 61 per-component documents plus `guidelines.bundle.json`.
54 have authored source; the other 7 are registry slugs whose guidance resolves
entirely through inheritance and `registryAliases`.

`dist/guidelines/coverage.md` is the documentation-debt backlog: every component
against the five domains, each cell a status. It is generated, so it cannot drift
from the `_meta.yml` files it summarises.

`dist/identity.json` is the identity ledger (chapter 03). `dist/canonical-sections.json`
is the catalogue of design section names.

## Content

22 source files in three buckets: `writing/` (11), `patterns/` (8), `product/` (3).

`writing/` and `product/` concatenate verbatim into `content/dist/global.md` and
produce `words-to-avoid.json`. `patterns/` takes a different path: it is parsed
into sections and fanned out into component guideline records by
`fanout-patterns.js`, which is why editing a content pattern changes files under
`components/dist/`.

`content/src/writing/voice-and-tone.md` is the design system's own published
guideline for product UI copy. It is not the same thing as the ecosystem bundle's
authoring voice file, and the two are edited in different repositories for
different audiences.

Schema: `schemas/content.json`, `schemas/words-to-avoid.json`.

## Accessibility

13 source sections, ordered by `_order.json`, carrying 32 anchored slugs. Derives
`accessibility/dist/a11y-index.json` (a slug to WCAG 2.2 AA map) plus a Pattern H
tree using the same engine as foundations.

This is the primary transversal taxonomy. Components and categories point into it
with `a11y_refs: [{ref: focus-keyboard, note: "..."}]`. The anchors are declared in
source as `{#slug}` rather than derived from heading text, which is principle P6
and the reason an editorial rename cannot break a consumer.

## App context

The product side: what the design system is being used to build.

| Kind | Count | What it is |
| --- | --- | --- |
| Apps | 3 | Studio, Explorer, Administration |
| Entities | 30 | Product concepts such as Dataset or Access Request |
| Patterns | 31 | Recurring UX patterns tied to real flows |
| Terminology | 33 | The words the products use |
| Recipes | 4 | Page recipes captured from the running product |

Recipes are addressed one at a time rather than folded into `app-context.json`,
because a single recipe can exceed 1400 lines and bundling them would make every
consumer pay for every archetype in order to read one.

Entities carry `relationships` with named predicates, which is the only place in
the substrate where a cross-reference has a domain-specific verb rather than a bare
slug ref.

Schemas: `app-context-app.json`, `app-context-entity.json`, `app-context-pattern.json`,
`app-context-recipe.json`, `app-context-term.json`, `app-context.json`.

## Tokens

463 token leaves in W3C DTCG format across 10 groups: color, spacing, border, size,
breakpoint, focus ring, font, icon, shadow, motion.

**Tokens are derived, not authored.** This is the domain people most often get
wrong, because the outputs sit at the domain root rather than under a `dist/`
folder, so the usual signal is absent.

```
foundations/src/color-primitives.md   the OKLCH shade formula and the palette bases
foundations/src/tokens.md             the semantic token mappings
tokens/src/figma-bindings-raw.json    harvested Figma bindings (the one authored file)
   -> npm run derive:tokens
   -> tokens/src/derived/{primitives,semantics,numerics}.tokens.json
   -> tokens/tokens.json, tokens/tokens.css
   -> tokens/token-reference.md, tokens/dist/tokens.dtcg.json
```

`tokens.json` discloses this itself in `$metadata.generatedBy`, and `tokens.css`
carries an auto-generated header. CI runs `derive:tokens` inside
`foundations-derive.yml`, so a foundations edit refreshes the tokens in the same
pull request.

**To change a token value, edit the foundations source**, not the output: a palette
base or the shade formula in `foundations/src/color-primitives.md`, a semantic
mapping in `foundations/src/tokens.md`. Editing `tokens.json` directly does not
survive the next derive.

`tokens/token-reference.md` is drift-guarded in the required check.

`tokens/src/figma-export/` is deliberately untracked. It is a local parity oracle
for the deriver, read by no script and covered by no manifest entry, so tracking it
would trip the orphan guard.

The motion group doubles as a transversal taxonomy: 8 anchored patterns in
`foundations/dist/tokens/motion.json#patterns` that components reference through
`motion_refs`.

## The transversal pattern

Three taxonomies are referenced rather than duplicated, and they all use one shape:

```yaml
a11y_refs:
  - { ref: focus-keyboard, note: "must be operable with Enter and Space" }
  - { ref: color-contrast }
```

| Taxonomy | Anchored in | Referenced as |
| --- | --- | --- |
| Accessibility | `accessibility/dist/a11y-index.json` | `a11y_refs` |
| Motion patterns | `foundations/dist/tokens/motion.json#patterns` | `motion_refs` |
| Foundations sections | `foundations/dist/foundations-index.json` | `foundations_refs` |

The array is named after the target domain, items are `{ref: <slug>}` plus an
optional `note`, the slug must exist in the target's dist, and the derive fails
fast when it does not. A new transversal taxonomy adopts the same shape so
consumers can write one adapter for all of them.

**The gap, stated plainly:** components reference the transversal taxonomies;
content does not. Content rules discuss tone without pointing into any anchored
taxonomy, so the symmetry principle P8 describes is incomplete on that side.
